# ИнвестСигнал — демонстрационный прототип

React-приложение с Python/FastAPI API и отдельным PostgreSQL. Данные общие для всех браузеров и сохраняются после перезапуска контейнеров. AI, сбор документов и авторизация пока не подключены; организации, оценки, источники и исторические метрики остаются демонстрационными.

## Запуск

Из этой папки:

```sh
docker compose up -d --build --wait
```

Откройте http://localhost:18473. Это полный стек из трёх контейнеров:

| Сервис | Назначение |
| --- | --- |
| `frontend` | Существующий React/Nginx контейнер; обслуживает UI и проксирует `/api` |
| `backend` | Python 3.12 / FastAPI; проверяет ввод и записывает изменения |
| `db` | PostgreSQL 17; данные в постоянном томе `postgres_data` |

Наружу опубликован только порт frontend. Backend и БД доступны внутри сети Compose. Один API worker, небольшой пул соединений и ограниченные настройки PostgreSQL подходят для небольшого демо на слабом сервере.

Порт меняется через `APP_PORT`:

```sh
APP_PORT=18474 docker compose up -d --build --wait
```

При необходимости скопируйте `.env.example` в `.env` и задайте порт/параметры БД. Пароль по умолчанию предназначен для демо; файл `.env` не отслеживается Git. Пароль существующей базы не меняется от редактирования переменной — PostgreSQL применяет её при создании пустого тома.

Запуск из `frontend` прежней командой тоже работает: её Compose-файл включает полный стек из родительской папки. Требуется Docker Compose 2.20+ для `include`.

## Проверка и остановка

```sh
docker compose ps
curl http://localhost:18473/healthz
curl http://localhost:18473/api/health
docker compose logs --tail=100 backend db
docker compose down
```

`/healthz` проверяет Nginx, `/api/health` — API и связь с БД. `down` сохраняет том с данными. Не используйте `down -v`, если хотите сохранить изменения: этот флаг удаляет БД.

## Поведение данных

- Backend выполняет версионированные SQL-миграции из `backend/migrations` и один раз загружает шесть карточек, четыре источника и пример аналитики из `backend/seed`.
- Повторный запуск, пересборка и перезапуск API не заменяют пользовательские изменения демонстрационными.
- Существующие данные localStorage остаются в браузере, но новая версия их не использует и автоматически не импортирует.
- Создание карточек, назначения, решения и тестовые повторы источников записываются в PostgreSQL. Генерацию ID обеспечивает БД; обновления отдельных полей используют блокировку строки.
- Карта получает координаты демонстрационных карточек из API. Для ручных сигналов координаты не выдумываются.
- Повтор источника симулирует успешный сбор и сохраняет статус/время; документы не загружаются.
- Исторические показатели аналитики остаются помеченными примерами. Текущая воронка рассчитывается по карточкам из API.
- CSV включает только одобренные карточки. Сохранение файла экспорта и изменение статусов выполняются одной транзакцией; файл можно загрузить повторно по ID.
- UI обновляется после действий, при возвращении в окно и раз в 15 секунд в видимой вкладке. Ошибка API предлагает повторить запрос и не сбрасывает общую БД.
- Демонстрационные ответственные — подписи, а не учётные записи. Авторизации нет.

## API

Документация: http://localhost:18473/api/docs. Схема: `/api/openapi.json`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/state` | Карточки, источники и пример аналитики одним запросом |
| GET | `/api/candidates` | Все карточки |
| GET | `/api/candidates/{id}` | Одна карточка |
| POST | `/api/candidates` | Ручной сигнал: company, sector, city, signal, source |
| PATCH | `/api/candidates/{id}` | status (review/approved/rejected), owner, nextAction |
| GET | `/api/sources` | Демонстрационные источники |
| POST | `/api/sources/{id}/retry` | Симуляция повторного сбора |
| GET | `/api/analytics` | Фиксированный исторический пример |
| POST | `/api/exports` | CSV одобренных карточек; ответ содержит csv, count, exportId |
| GET | `/api/exports/{exportId}` | Повторное скачивание сохранённого CSV |
| GET | `/api/health` | Готовность API/БД |

## Разработка и проверки

Frontend сохраняет существующие настройки React/Vite/MapLibre и контейнерную сборку. Локальная разработка при работающем Compose:

```sh
cd frontend
npm ci
npm run dev
```

Vite проксирует `/api` к http://127.0.0.1:18473. Для другого порта задайте `API_PROXY_TARGET` в `frontend/.env.local`.

Проверки frontend:

```sh
npm run typecheck
npm test
npm run build
npm run test:browser:install
npm run test:e2e
```

UI-тесты используют изолированные HTTP-фикстуры. Проверка реального стека из `frontend`:

```sh
E2E_STACK_URL=http://127.0.0.1:18473 npm run test:e2e -- tests/e2e/backend.spec.ts
```

API-тесты запускаются из корня приложения, в отдельном временном контейнере. Они создают и удаляют отдельные тестовые базы PostgreSQL, не меняя демонстрационную базу:

```sh
docker compose run --rm --no-deps --user root backend sh -c 'pip install --no-cache-dir -r requirements-test.txt && python -m pytest -q'
```

Проверяются сохранение при повторной инициализации, конкурентное создание/редактирование, валидация, неизвестные ID, одновременный экспорт и повторное скачивание CSV.

## Сервер и HTTPS

Конфигурация обслуживает HTTP на внутреннем порту 8080. Существующий TLS-прокси сервера должен направлять запросы к frontend, включая `/api`. Удалённая HTTPS-конфигурация и сервер этой задачей не изменяются. При переносе на Samsung/x86-64 собирайте образы на сервере или для `linux/amd64`; образ, собранный на Apple Silicon, по умолчанию ARM64.

Старый статический Dockerfile в корне сохранён как артефакт промо; основной `compose.yaml` использует уже существующий `frontend/Dockerfile`.
