# ИнвестСигнал — пилот

React-приложение с Python/FastAPI API и PostgreSQL. Система сама собирает новости из 24 открытых источников (региональные, федеральные и отраслевые СМИ, Яндекс Дзен), отбирает сигналы об инвестиционных проектах Свердловской области с помощью GigaChat, оценивает их и складывает в очередь аналитика. Инициатора проекта можно проверить по ИНН в Контур.Фокусе: банкротство, суды, приставы, блокировки счетов, достоверность ЕГРЮЛ и владельцы сводятся в зелёный, жёлтый или красный вердикт. Встроенный ассистент работает с теми же данными через инструменты: ищет карточки, меняет статусы по просьбе, запускает сбор и разбор, проверяет компании.

Шесть демонстрационных карточек из первой версии остаются в базе с меткой «Демо». Карточки из пайплайна помечены «ИИ». Доступ закрыт HTTP Basic Auth для одного пользователя; регистрации нет.

## Запуск

Из этой папки:

```sh
cp .env.example .env   # впишите AUTH_PASSWORD, LLM_BASE_URL и LLM_API_KEY
docker compose up -d --build --wait
```

Откройте http://localhost:18473. Стек из четырёх контейнеров:

| Сервис | Назначение |
| --- | --- |
| `frontend` | React/Nginx; обслуживает UI и проксирует `/api` |
| `backend` | Python 3.12 / FastAPI; API, чат-ассистент |
| `worker` | Тот же образ, `python -m app.worker`: сбор RSS по расписанию и разбор документов |
| `db` | PostgreSQL 17; данные в томе `postgres_data` |
| `dzen` | По желанию: сбор Дзена в headless-браузере, образ `backend/Dockerfile.dzen` на базе Playwright. Включается так: `docker compose --profile dzen up -d --build` |
| `collector` | По желанию: сбор источников событий по API (`SOURCE_KINDS` в `compose.yaml`), чтобы длинные выгрузки не задерживали RSS и разбор. Пока подключённых API-адаптеров нет, сервис выключен; включается так: `docker compose --profile events up -d` |

Наружу опубликован только порт frontend. Порт меняется через `APP_PORT`. Без `LLM_API_KEY` воркер только собирает документы, а чат и разбор отвечают «ИИ не настроен». Без `FOCUS_API_KEY` блок проверки инициатора сообщает, что Контур.Фокус не настроен.

Пароль БД по умолчанию предназначен для демо. Файл `.env` не отслеживается Git — ключ ИИ храните только там.

### Вход

В `.env` задайте `AUTH_USERNAME=poc_user` и `AUTH_PASSWORD` — длинный уникальный пароль из ASCII-символов. Имя пользователя можно изменить (ASCII, без двоеточий); пароль может содержать двоеточия. Без `AUTH_USERNAME` используется `poc_user`. Без непустого `AUTH_PASSWORD` API не запускается. Секреты читаются только бэкендом при запуске и не включаются в сборку браузера.

При открытии сайта браузер покажет стандартное окно входа. Используются встроенные механизмы FastAPI HTTPBasic и Nginx auth_request: Nginx проверяет доступ к HTML и ресурсам через API, а API проверяет каждый запрос самостоятельно, включая чат, запуск разбора и документацию. Регистрации и дополнительных аккаунтов нет. Для скриптов используйте HTTP Basic Auth. Без входа доступны только `/healthz` и `/api/health` для проверки работоспособности.

На публичном сервере используйте HTTPS на внешнем TLS-прокси: HTTP Basic передаёт учётные данные с каждым запросом. После смены учётных данных пересоздайте API (`docker compose up -d --wait backend`); браузер запросит новый пароль. Воркер продолжает сбор и разбор по расписанию в пределах бюджета независимо от входа пользователя.

Деплой на сервер, заполнение секретов, обновление существующей установки и резервная копия БД: **[DEPLOYMENT.md](DEPLOYMENT.md)**. Все настройки из `.env.example`, включая модели, бюджет и расписание воркера, передаются API и воркеру. После правки `.env` контейнеры нужно пересоздать через `docker compose up -d --wait`; `restart` не подхватывает новые значения.

## Пайплайн

```
RSS-ленты, поиск Дзена ──► documents (new)
  1. префильтр без ИИ: кликбейт-заголовки (для Дзена порог строже); ≥2 разных «инвестиционных» корня;
     для нерегиональных лент — упоминание области/муниципалитета
  2. эмбеддинг EmbeddingsGigaR; косинус ≥ 0.93 с уже разобранным документом → повтор, приклеивается к той же карточке без LLM
  3. триаж GigaChat-3-Pro (JSON Schema): сигнал ли это, компания, муниципалитет, цитата, уверенность
  4. компания уже есть в очереди → документ добавляется доказательством, растёт «Уверенность»
  5. иначе GigaChat-3-Pro готовит карточку: резюме, сумма, стадия, факторы 0–100, рекомендация
```

Итоговая оценка считается в коде: 0.35·Релевантность + 0.25·Уверенность + 0.2·Региональный эффект + 0.2·Срочность. Координаты берутся из справочника центров муниципалитетов (`backend/app/geo.py`), поэтому точность — муниципалитет.

Этапы документа: `new` → `skipped` (фильтр), `rejected` (ИИ), `signal` (новая карточка), `merged` (добавлен к карточке), `error` (три неудачные попытки). Если GigaChat отвечает шаблонным отказом (фильтр «чувствительных тем») вместо JSON, документ сразу получает `rejected` с текстом отказа, без повторов. Вся лента видна на странице «Источники».

Если в тексте новости или в ответе модели есть ИНН компании (с верной контрольной суммой), он сохраняется в карточке, и при `FOCUS_AUTO_CHECK=1` инициатор сразу проверяется в Контур.Фокусе.

| СМИ УрФО и деловые | URA.news, Уралинформбюро, ФедералПресс, УралПолит.Ru, Коммерсантъ-Урал, Деловой квартал |

Федеральные и окружные ленты, а также региональные ленты с федеральными новостями (ЕАН) помечены `regional: false`: документ проходит дальше, только если в нём упомянута область или её муниципалитет. Битая запись в ленте не роняет всю ленту: при ошибке XML записи разбираются по одной.

У Дзена нет RSS и публичного API, а страницы отрисовываются скриптом. Поэтому сервис `dzen` открывает поиск Дзена в headless-браузере, как обычный читатель, и забирает ссылки, заголовки и анонсы публикаций. Если Дзен показывает капчу, сбор останавливается с ошибкой источника; обходить её мы не пытаемся. Локально без Docker: `pip install -r requirements-dzen.txt` и `DZEN_BROWSER_CHANNEL=chrome` (системный Chrome); воркер собирает Дзен, если в `SOURCE_KINDS` есть `dzen`.

Фильтр кликбейта (`app/clickbait.py`) взвешивает признаки заголовка: интрига вместо факта («вы не поверите», «шок», «вот почему»), обращение к читателю, «уникальный завод, который может увидеть каждый», списки «5 причин», вводные «во-первых», капслок, эмодзи и «!!». Для Дзена документ отсеивается при сумме ≥2, для СМИ — при ≥3. Причина видна в ленте документов.

Источники описаны в `backend/seed/sources.json` и синхронизируются с БД при каждом старте; время последнего запуска и ошибка сохраняются. Ленты скачиваются напрямую (`trust_env=False`) с честным User-Agent. Сертификат Минцифры лежит в `backend/certs`, он нужен части региональных сайтов. Дополнительный CA положите на сервере в `certs/company-ca.pem`, а в `.env` задайте `EXTRA_CA_FILE=/run/investsignal/certs/company-ca.pem`: каталог монтируется в API и воркер только для чтения и игнорируется Git.

### Источники событий и адаптеры

Кроме публикаций, сервис хранит структурированные события из внешних систем: вакансии, торги, разрешения, техприсоединение. Они лежат в отдельной таблице `source_events`, а не в `documents`.

- **Адаптеры** (`backend/app/sources/`). У каждого типа источника свой адаптер с общим интерфейсом `SourceAdapter`: `availability()` проверяет настройки без сети, `check()` делает лёгкий запрос, `fetch(cursor)` отдаёт данные батчами (документы и/или события, курсор, признак полной выгрузки). Реестр: `register(kind)` и `adapter_for()`. RSS и Дзен — обёртки над прежним сборщиком, разбор лент не менялся. Адаптер `import` принимает строки от организаций (`event_from_row` проверяет ИНН, ОГРН, даты, муниципалитет, кадастровый номер); API загрузки файлов появится позже. Адаптер `trudvsem` («Работа России») описан ниже. Типы `hh`, `torgi`, `egrz` пока только зарезервированы в реестре (`PLANNED`): адаптер-заглушка отвечает «Требуется настройка» и не делает ни одного запроса. В `seed/sources.json` таких источников нет, поэтому в интерфейсе они не показываются; запись появится вместе с настоящим адаптером.
- **Раннер** (`sources/runner.py`). На каждый источник — advisory lock: параллельный запуск получает статус `skipped`. Каждый запуск пишется в `source_runs` со счётчиками (получено, новых, обновлённых, без изменений, отклонённых, повторов) и ошибкой. После каждого батча данные, курсор и COMMIT сохраняются, поэтому сбой на следующей странице не теряет уже полученное. Любая ошибка остаётся внутри запуска и не обрывает такт worker. После неудачи источник событий повторяется через 5, 10, 20… минут, но не реже расписания; 401/403 и ошибки формата ждут обычного расписания. RSS и Дзен после любой ошибки, в том числе капчи и 403 от антибота, ждут полный интервал `scheduleMinutes`, как до адаптеров. Если выгрузка оборвалась на середине, следующий запуск продолжает её по курсору; время начала выгрузки (`snapshot_started_at`) сохраняется до последнего батча и передаётся в `snapshot_finished()`, чтобы адаптер не закрыл записи, полученные в предыдущем запуске. `request_json()` повторяет запрос при сетевых сбоях, 5xx и 429 (с учётом `Retry-After`). Поля `lastRun`, `lastError` и `status` в `sources` обновляются как раньше.
- **Дедупликация.** `UNIQUE (source_id, dedup_key)`: ключ `id:<внешний ID>` или `h:<sha256>` значимых полей. Повторная загрузка того же события только обновляет `last_seen_at`. Если содержимое изменилось, прежняя версия уходит в `source_event_versions`, а событие снова проходит связывание: прежние связи правил снимаются, и доказательство остаётся только в карточках, с которыми событие связано заново как `confirmed` или `probable`. Из `raw`, `metrics` и деталей удаляются NUL-символы, а NaN и бесконечности заменяются на `null`: jsonb их не принимает. Муниципалитет приводится к справочнику области; если его там нет (другой регион или посёлок вне списка), сохраняется написание источника. В `raw` хранится исходный JSON по белому списку полей, без персональных данных.
- **Типы событий** — расширяемый справочник `backend/seed/event_types.json`: категория, полярность и политика связи `company`, `context` (лот без победителя) или `aggregate` (одиночная вакансия). Типы, удалённые из seed, помечаются `deprecated`, а не удаляются.
- **Связь с карточками** (`backend/app/linking.py`, без ИИ, каждый такт worker). Первое сработавшее правило:
  1. `aggregate` — событие учитывается только в агрегированных сигналах;
  2. `context` — контекст, компания не привязывается;
  3. нет ИНН (или только ОГРН) — на ручную проверку;
  4. карточек с этим ИНН нет — новая карточка `origin: "events"`, если за `windowDays` (180) набралось не меньше `minCategoriesForCard` (2) разных категорий положительных событий в одном муниципалитете из справочника области; иначе событие ждёт, при разных муниципалитетах или месте вне справочника — ручная проверка;
  5. муниципалитет события не найден в справочнике области — ручная проверка с предложением карточек компании;
  6. одна карточка — тот же муниципалитет (или он не указан) даёт связь `confirmed` и доказательство в карточке, другой — ручную проверку;
  7. несколько карточек — `probable`, если совпал ровно один муниципалитет, иначе ручная проверка.

  Пороги — в `backend/seed/linking_rules.json` или в файле из `LINKING_RULES_PATH`. Доказательство из события добавляется в `evidence` с необязательными полями `kind: "event"`, `eventId`, `eventType` и `occurredAt` (ISO-дата); у старых карточек их нет, и они остаются валидными. Бонус «Уверенности» за событие не начисляется. Автопроверка Фокуса для карточек из событий по умолчанию выключена (`FOCUS_AUTO_CHECK_EVENTS=0`), чтобы ИНН работодателей не исчерпали лимит.
- **Ручной запуск.** `POST /api/sources/{id}/collect` для RSS и Дзена собирает сразу, как раньше. Источник событий внутри HTTP-запроса не собирается никогда: готовый ставится в очередь (`queued: true`), потому что полная выгрузка идёт минутами и не укладывается в таймауты nginx и frontend. Отключённый источник и источник без доступа (`connection: "no_access"`) получают 409; ненастроенный только записывает запуск с причиной, без сети. Очередь подхватывает worker, у которого этот тип есть в `SOURCE_KINDS` (в `compose.yaml` — сервис `collector` из профиля `events`). Ассистент без `source_id` собирает только новостные источники.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `SOURCE_RETRY_ATTEMPTS` | `3` | Попыток HTTP-запроса внутри одного запуска; `1` — без повторов |
| `SOURCE_BACKOFF_BASE_MINUTES` | `5` | Первая пауза после неудачного запуска, дальше удваивается |
| `SOURCE_MAX_RETRY_AFTER` | `300` | Сколько секунд максимум ждать по `Retry-After`; дольше — запуск откладывается |
| `SOURCE_RUN_STALE_MINUTES` | `60` | Через сколько минут зависший запуск при старте worker помечается ошибкой |
| `EVENT_LINK_BATCH` | `200` | Событий на один такт связывания |
| `FOCUS_AUTO_CHECK_EVENTS` | `0` | Проверять в Фокусе карточки, созданные из событий |
| `LINKING_RULES_PATH` | пусто | Свой файл порогов вместо `seed/linking_rules.json` |

### «Работа России» и кадровые сигналы

Источник `trudvsem` в группе «Кадровые источники» собирает вакансии работодателей Свердловской области из открытого API портала. Ключ не нужен. Сами по себе вакансии карточек не создают: из них считаются показатели по работодателю и кадровые сигналы виртуального источника `hiring-signals` («Кадровая аналитика»).

**API** (документация [trudvsem.ru/opendata/api](https://trudvsem.ru/opendata/api), схема `application.wadl`, ответы проверены 25.11.2026):

- запрос `GET https://opendata.trudvsem.ru/api/v1/vacancies/region/6600000000000`; код региона взят из ответа API (`region.region_code`, «Свердловская область»), в регионе около 16,4 тыс. вакансий;
- `offset` — номер страницы, а не смещение; `limit` — не больше 100;
- `modifiedFrom` и `modifiedTo` — время изменения в ISO 8601, обе границы включительно, `Z` понимается как UTC;
- на один запрос API отдаёт не больше 10 000 записей: страница за этой границей отвечает HTTP 500. Поэтому полную выгрузку одним списком не получить. Адаптер делит диапазон пополам по времени изменения, пока в окне не останется не больше 9 000 вакансий, и обходит окна от старых к новым. Последнее окно открыто сверху, поэтому вакансия, изменённая во время обхода, всё равно попадает в выгрузку;
- лимиты частоты не опубликованы. Между страницами — пауза `TRUDVSEM_PAGE_DELAY_SECONDS`, 429 и 5xx повторяются по общим правилам раннера;
- при копировании данных портал требует ссылку на trudvsem.ru: у каждой вакансии и сигнала сохраняется ссылка на первоисточник.

**Сбор.** Каждые 6 часов (`scheduleMinutes: 360`) идёт инкремент: `modifiedFrom` = начало прошлого прохода минус `TRUDVSEM_OVERLAP_MINUTES`. Первый запуск и далее раз в `TRUDVSEM_FULL_SYNC_DAYS` дней — полная выгрузка. Позиция прохода (окна и страница) хранится в курсоре. Если запуск упал или упёрся в `TRUDVSEM_MAX_PAGES`, он получает статус `partial`, и следующий запуск продолжает с той же страницы. После полной выгрузки вакансии, которых в ней не было, закрываются (`closed_at`). Закрытие выполняется, только если выгрузились все окна и страницы; частичная выгрузка ничего не закрывает. Закрытая вакансия, снова найденная в выгрузке, открывается. Вручную сбор запускается кнопкой «Собрать»: он ставится в очередь worker. Полная выгрузка занимает около 175 запросов.

**Что сохраняется.** Каждая вакансия — событие `vacancy_opened` (`dedup_key = id:<ID вакансии>`) плюс строка `vacancy_details`:

- работодатель: название, ИНН и ОГРН (только с верной контрольной суммой, иначе `null`), КПП, ID работодателя на портале;
- вакансия: название, обязанности и требования (до 2000 знаков), адрес, координаты, муниципалитет;
- даты публикации (`creation-date`) и изменения (`date_modify`);
- число рабочих мест, зарплата, тип занятости, график, специализация, код профессии, ссылка на вакансию.

`raw` собирается по белому списку полей. В нём нет `contact_person`, `contact_list` и `company.email`. Телефоны и e-mail в тексте обязанностей и в адресе заменяются на `[телефон]` и `[e-mail]`. Сведений о соискателях API не отдаёт, и они не запрашиваются. Вакансии чужого региона и записи без идентификатора работодателя отбрасываются и попадают в счётчик «отклонено».

**Общий модуль вакансий** (`backend/app/vacancies/`, его же будет использовать HeadHunter):

- `model.py` — нормализованная `Vacancy`.
  - Ключ работодателя: `inn:<ИНН>`, иначе `ogrn:<ОГРН>`, иначе `trudvsem:<ID на портале>`. Название в ключ не входит, автоматического объединения работодателей по названию нет.
  - Муниципалитет определяется по части адреса «г Город» или по району и приводится к справочнику области. Город вне справочника сохраняется как написан. Если указан только посёлок, муниципалитет `null`.
  - Отпечаток (`fingerprint`) — работодатель, название без скобок, муниципалитет и вилка зарплаты с округлением до 5 000.
- `categories.py` и `seed/vacancy_categories.json` (путь меняется через `VACANCY_CATEGORIES_PATH`). Категории задаются регулярными выражениями по названию вакансии: технологи, инженеры, операторы линий, наладчики, начальники производства, директора предприятий, рабочие профессии. Первая совпавшая категория определяет профиль: `production`, `engineering`, `production_management` или `executive`. Если ни одна не совпала, профиль берётся по специализации портала, иначе `other`.
  - Исключаются из сигналов кадровые агентства, организации с бюджетными формами в названии (МБОУ, ГАУЗ, ФКУ…), администрации, ведомства, а также работодатели, у которых не меньше половины вакансий в образовании, здравоохранении или госслужбе. Муниципальные и федеральные унитарные предприятия не исключаются. Исключённые работодатели учитываются в счётчиках, но сигналов не получают.
  - Справочник проверяется pydantic при старте: битый файл останавливает запуск, а не пропускается.
- `store.py` — запись `vacancy_employers` и `vacancy_details`, закрытие пропавших вакансий, межисточниковые дубли. Вакансия с тем же отпечатком из другого источника или перепубликация «Вакансия интернет ресурса» в пределах ±30 дней получает `duplicate_of` на более раннюю. Дубли не участвуют в показателях.
- `aggregates.py` — показатели работодателя на дату:
  - актуальные вакансии и сумма рабочих мест (если число не указано, считается одно место);
  - новые за 30 и 90 дней — по дате публикации на портале, а не по первому появлению в InvestGuard, поэтому первая выгрузка не создаёт всплеск «новых»;
  - производственные, инженерные и управленческие вакансии;
  - динамика к снимкам D−30 и D−90;
  - новые для компании муниципалитеты.

  Каждый день пишется снимок в `vacancy_employer_snapshots`. Пока работодатель наблюдается меньше `minHistoryDays` (60 дней), динамика и новые муниципалитеты равны `null` с причиной «недостаточно истории наблюдения»: процент роста не выдумывается.
- `signals.py` и `seed/hiring_signals.json` (путь меняется через `HIRING_SIGNALS_PATH`, все пороги настраиваются):

| Сигнал | Условие по умолчанию |
| --- | --- |
| `vacancy_mass_hiring` | Новых вакансий за 30 дней не меньше, чем 3 × медиана месячного числа новых вакансий работодателя за историю наблюдения. Есть минимум по размеру работодателя: 5, 12 или 30 вакансий. Без истории действует повышенный минимум 15 с пометкой «без базы сравнения» |
| `vacancy_growth` | Актуальных вакансий в 1,5 раза больше, чем 90 дней назад, и прирост не меньше 5. Без истории наблюдения не рассчитывается |
| `vacancy_new_municipality` | Не меньше 2 производственных, инженерных или управленческих вакансий в муниципалитете, где за предыдущий год у работодателя вакансий не было, при условии что раньше он нанимал в другом месте. Нужна история |
| `vacancy_production_launch` | За 90 дней в одном муниципалитете не меньше 3 разных категорий из набора запуска (технологи, инженеры, операторы линий, наладчики, начальники производства, директора), среди них хотя бы одна управленческая |

Сигнал — событие источника `hiring-signals` с ключом `тип:работодатель:муниципалитет:месяц начала эпизода`. Пока условие выполняется, ежедневный пересчёт обновляет тот же сигнал (старое содержимое уходит в версии), а не создаёт новый. Когда условие перестаёт выполняться, сигнал получает статус `ended`. В `raw` лежат показатели работодателя, применённые пороги и до 50 вакансий-оснований с ссылками. Сигнал без ИНН уходит на ручную проверку с причиной «нужно сопоставить с юрлицом». Все кадровые сигналы относятся к одной категории событий `hiring`, поэтому без событий другой категории карточку они не создают (`minCategoriesForCard` в `linking_rules.json`).

**Где считается.** Показатели и сигналы считает тот worker, у которого в `SOURCE_KINDS` есть `trudvsem` (в `compose.yaml` это сервис `collector`). После каждого сбора пересчитываются работодатели, чьи вакансии изменились. Раз в сутки пересчитываются все работодатели и применяется отредактированный справочник категорий. Кнопка «Собрать» у «Кадровой аналитики» запускает полный пересчёт. На странице «Источники» у «Работы России» показаны число вакансий и актуальных вакансий, число работодателей и сигналов (поле `hiring` в `GET /api/sources`). Там же видны последний сбор и ошибки.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `TRUDVSEM_BASE_URL` | `https://opendata.trudvsem.ru/api/v1` | Адрес API |
| `TRUDVSEM_REGION_CODE` | `6600000000000` | Код региона из API (13 цифр) |
| `TRUDVSEM_PAGE_DELAY_SECONDS` | `0.5` | Пауза между страницами |
| `TRUDVSEM_MAX_PAGES` | `300` | Запросов за один запуск; остальное продолжит следующий запуск |
| `TRUDVSEM_FULL_SYNC_DAYS` | `7` | Как часто делать полную выгрузку с закрытием пропавших вакансий |
| `TRUDVSEM_OVERLAP_MINUTES` | `60` | Перекрытие инкремента |
| `VACANCY_CATEGORIES_PATH`, `HIRING_SIGNALS_PATH` | пусто | Свои справочник категорий и пороги вместо `backend/seed/*.json` |

**Ограничения.**

- История наблюдения начинается с первой выгрузки. Рост и новые муниципалитеты появятся не раньше чем через 60 дней, рост к D−90 — через 90 дней. Пока истории нет, массовый найм у крупных работодателей с высокой текучестью (розница, доставка) может срабатывать по повышенному минимуму. Такие сигналы помечены «без базы сравнения».
- Справочник муниципалитетов содержит 42 центра. Посёлки без района остаются без муниципалитета, города вне справочника сохраняются как написаны и при связывании уходят на ручную проверку.
- Вакансия, которая во время полной выгрузки сдвинулась между страницами, может быть ошибочно закрыта. Она откроется при следующей встрече в выгрузке.
- Пороги — стартовые. Перед включением в отчётность их нужно проверить на размеченной выборке.
- Резервный канал, если API станет недоступен: наборы открытых данных портала в XML («Вакансии Уральского федерального округа» на opendata.trudvsem.ru). Пока не реализован; при недоступности API источник показывает ошибку, а данные не подменяются.

### Бюджет ИИ

Каждый вызов пишется в `llm_usage` с токенами и стоимостью (заголовок `x-litellm-response-cost`, иначе — по таблице цен в `app/llm.py`). При достижении `LLM_BUDGET_USD` или `LLM_DAILY_BUDGET_USD` разбор останавливается, документы остаются в очереди, API отвечает 429. Первый прогон на 451 документе стоил около $0.10: префильтр отсекает ~97% документов.

| `LLM_SMART_MODEL` | `GigaChat-3-Pro` | Карточки и чат |
| `LLM_EMBED_MODEL` | `EmbeddingsGigaR` | Поиск повторов |
| `LLM_BUDGET_USD` / `LLM_DAILY_BUDGET_USD` | `45` / `3` | Общий и дневной лимит |
| `PIPELINE_INTERVAL_SECONDS` / `PIPELINE_BATCH` | `60` / `20` | Такт воркера и сколько документов он разбирает за такт |
| `PIPELINE_WORKER` | — | `1` запускает воркер внутри API-процесса (удобно локально) |
| `SOURCE_KINDS` | `rss` | Какие типы источников собирает этот процесс, через запятую: `rss`, `dzen`, типы API-адаптеров (сервис `collector`). Источники `import` пополняются только загрузкой файла |
| `PIPELINE_PROCESS` | `1` | `0` — только сбор без разбора (так работает сервис `dzen`) |

### Проверка инициатора: Контур.Фокус

Проверка запускается кнопкой в карточке (поле «ИНН компании-инициатора»), через ассистента («проверь INV-1018, ИНН …») или автоматически, если ИНН есть в тексте. По ИНН вызываются десять методов API3:

| Что проверяем | Методы Фокуса |
| --- | --- |
| Статус, регистрация, реквизиты | `req` |
| Финансовая устойчивость, налоги, экспертный рейтинг отчётности | `financeAnalytics` |
| Банкротство: процедуры, сообщения, намерения кредиторов | `bankruptcyAnalytics` |
| Арбитраж: иски к компании, проигранные дела, налоговые споры | `courtAnalytics` |
| Исполнительные производства, в том числе по зарплате | `fsspAnalytics` |
| Блокировки счетов ФНС | `fnsBlockedBankAccounts`, `legalAnalytics` |
| Недостоверность ЕГРЮЛ, дисквалификация, заявления о ликвидации и сменах | `legalAnalytics` |
| Аффилированность: массовый адрес и руководитель, связанные банкроты | `linkAnalytics` |
| Конечные бенефициары, уставный капитал | `beneficialOwners` |
| Собственные рейтинги Фокуса | `scoring` |

Методов `/arbitr`, `/fssp`, `/gpd`, `/relationships` из постановки в API3 нет, их роль выполняют аналитические методы из таблицы. Поиск по названию (`suggest`) в тариф ключа не входит, поэтому ИНН вводит аналитик или он находится в тексте.

**Лимит.** Ключ даёт 1000 компаний на каждый метод до 31.01.2027, повторные запросы по той же компании лимит не тратят. Ответы хранятся в таблице `focus_checks`; новая компания проверяется, только пока их меньше `FOCUS_INN_LIMIT`. Неверная контрольная сумма ИНН отсекается до обращения к API. Остаток лимита виден на странице «Источники» и в блоке проверки.

**Флаги и вердикт** (`app/risk.py`). Вердикт определяется худшим флагом: есть красный — красная зона, иначе есть жёлтый — жёлтая, иначе зелёная. Пороги по судам и приставам считаются от выручки, поэтому 2,5 млн ₽ долгов для компании с выручкой 11 млрд — жёлтый флаг, а не красный.

| Уровень | Флаги |
| --- | --- |
| Красный (стоп-фактор) | недействующая, ликвидация или банкротство по ЕГРЮЛ; заявление о ликвидации; процедура или сообщения о банкротстве; дела о банкротстве против компании; недостоверные сведения ЕГРЮЛ; дисквалифицированный руководитель; блокировка счетов ФНС; высокий риск по «Знай своего клиента»; не сдаёт налоговую отчётность больше года; отрицательные чистые активы; слабый экспертный рейтинг (CCC и ниже); иски к компании ≥25% выручки; долги по зарплате у приставов; долги у приставов ≥ max(1 млн ₽, 1% выручки); низкий рейтинг благонадёжности Фокуса |
| Жёлтый (нужна проверка) | реорганизация; компания моложе года; намерение кредиторов банкротить; банкротство руководителя или учредителя; налоговый долг; Фокус рекомендует доппроверку; смена руководителя, владельцев или адреса за месяц; нет отчётности за последний год; убыток; падение выручки >30%; иски 5–25% выручки; налоговые споры ≥1 млн ₽; небольшие долги у приставов; ≥5 связанных компаний ликвидированы через банкротство; массовый адрес или руководитель (≥10 компаний); иностранные конечные владельцы; минимальный уставный капитал; средний рейтинг благонадёжности или низкие другие рейтинги Фокуса |
| Зелёный (плюс к надёжности) | работает больше 5 лет; крупная прибыльная компания (выручка ≥1 млрд ₽); сильный экспертный рейтинг; нет исполнительных производств; нет блокировок счетов; известен конечный владелец |

Пример на реальных данных: АО «ЕЗ ОЦМ» получает жёлтую зону — нет отчётности после 2021 года и 28 связанных компаний ликвидированы через банкротство, при этом нет долгов у приставов и блокировок, выручка 11 млрд ₽, известен владелец.

Результат сохраняется в карточке (`inn`, `risk`), попадает в CSV-выгрузку (колонки «ИНН» и «Риск (Контур.Фокус)») и показывается точкой рядом с ID в очереди.

### Ассистент

`POST /api/chat` получает историю диалога и крутит цикл tool calling (до 6 шагов) на GigaChat-3-Pro. Инструменты: `search_candidates`, `get_candidate`, `update_candidate`, `create_signal`, `search_documents`, `pipeline_status`, `collect_sources`, `process_documents` (не больше 10 документов за раз), `check_company` (проверка инициатора в Контур.Фокусе; тратит лимит, поэтому вызывается только по просьбе пользователя). Ответ содержит трассировку вызовов, а UI показывает, что ассистент сделал. Тексты новостей передаются модели как данные; менять карточки она должна только по явной просьбе пользователя.

Без Docker: PostgreSQL 14+, Python 3.11–3.12, Node 22+.

```sh
cd backend
python3.12 -m venv .venv && .venv/bin/pip install -r requirements-test.txt
set -a && . ../.env && set +a
PGHOST=127.0.0.1 PGUSER=postgres PGPASSWORD= PGDATABASE=investsignal PIPELINE_WORKER=1 \
  .venv/bin/uvicorn app.main:app --port 18000
```

```sh
cd frontend
npm ci
API_PROXY_TARGET=http://127.0.0.1:18000 npm run dev
```

Проверки:

```sh
cd frontend && npm run typecheck && npm test && npm run build
cd backend && DATABASE_URL=postgresql+psycopg://postgres@127.0.0.1:5432/postgres .venv/bin/python -m pytest -q
```

Бэкенд-тесты создают и удаляют временные базы. LLM и RSS в них подменены через `httpx.MockTransport`, поэтому тесты не тратят бюджет. Контур.Фокус и браузер Дзена тоже подменены; фикстура Фокуса — урезанный реальный ответ без персональных данных. Проверяются сбор, разбор битых лент, кликбейт, Дзен, префильтр, склейка повторов, карточка, отказы GigaChat, бюджет, цикл инструментов чата, скоринг рисков, кеш и лимит Фокуса, а также сохранение данных, конкурентные изменения, валидация и экспорт. Источники событий проверяются тестовым адаптером через `MockTransport`: сохранение и `raw`, повторная загрузка и версии, ошибки 500/429/403 и битый JSON, ненастроенный источник без запросов, правила связи с карточками, перепривязка изменённого события вместе с доказательством, место вне справочника области, NUL и NaN в `raw`, полный интервал RSS и Дзена после ошибки, начало выгрузки после частичного запуска, сохранность старых карточек после миграции и фильтры API. Тесты сами входят в API по HTTP Basic (`AUTH_PASSWORD` по умолчанию `local-test`). В Compose:

```sh
docker compose run --rm --no-deps --user root backend sh -c 'pip install --no-cache-dir -r requirements-test.txt && python -m pytest -q'
```

## Сервер и HTTPS

Конфигурация обслуживает HTTP на внутреннем порту 8080. TLS-прокси сервера должен направлять запросы к frontend, включая `/api`. Если прокси работает на самом сервере, задайте `APP_BIND=127.0.0.1`: приложение будет доступно через прокси и локально. По умолчанию `APP_BIND=0.0.0.0`, `APP_PORT=18473`. На x86-64 сервере собирайте образы там же или для `linux/amd64`.

Старый статический Dockerfile в корне сохранён как артефакт промо; основной `compose.yaml` использует `frontend/Dockerfile`.
